# 机房换路放行服务（FastAPI）

值班员为一个目的网段录入出口、最多 12 台路由器的新旧下一跳、各入口流量和有向链路容量，
按批申请下发新配置。服务端对“本批设备 + 已放行但尚未确认的设备”穷举所有新旧路由组合，
保证无论这些设备以什么先后顺序切换，流量都能到达出口，且每条有向链路上的合计流量不超过容量。
任一组合出现**断路、环路、超载**即整批退回，保留原放行记录，并在响应中标出故障位置。

## 裁决模型

对每个目的网段维护三组设备：

| 分组 | 含义 | 裁决时使用的路由 |
| --- | --- | --- |
| `confirmed` | 已放行且已登记成功回执 | 强制**新路由** |
| `pending` | 已放行但尚未确认 | 新、旧路由都可能生效 |
| 本批申请设备 | 本次申请下发新配置 | 裁决期间尚未切换，新、旧都可能 |
| 其余设备 | 不在任何批次中 | 保持**旧路由** |

不确定设备集合 `U = pending ∪ 本批`（最多 12 台），穷举 `2^|U|`（最多 4096）种组合，
逐场景沿路由表逐跳追踪每个入口的流量：

- 下一跳不存在或两者间没有录入有向链路 → **断路**，位置为中断处（如 `r1 -> r3`）；
- 再次进入路径上已出现的节点 → **环路**，位置为从入口开始的完整转发路径（如 `r1 -> r2 -> r4 -> r3 -> r4`）；
- 链路上汇聚的入口流量合计超过容量 → **超载**，位置为该链路并附 `load/capacity`。

全部场景安全才放行；放行后本批设备进入 `pending`。登记成功回执后设备转入 `confirmed`，
之后的裁决按新路由计算。退回不改变任何放行状态，申请记录仍留痕可审计。

并发安全：所有写操作在同一把 `asyncio.Lock` 内完成，并发申请按裁决时刻已登记的
批次和回执串行判断，后一个申请看到的一定是前一个落库后的状态。

## 入口限速单（检修降容）

机房检修要临时调低一条有向链路的容量时，值班员开立**入口限速单**：填写链路的新容量
（整数 Mbps，<=100 万），并按优先级列出各入口的保底速率（整数 Mbps，<=100 万）。
限速值分配：**先留足所有保底，再按优先级顺序让各入口尽量保住原速率**，剩余额度用完即止；
未列入限速单的入口不被限速。保底合计超过新容量即“保底已超容”，试算直接不通过。

生命周期：

| 阶段 | 接口 | 说明 |
| --- | --- | --- |
| 试算 | `POST /plans/rate-limits` | 以待确认设备（pending）的全部新旧组合，按“新容量 + 限速后流量”核算能否到达出口且各链路不超容；断路/成环/保底超容则返回导致失败的设备状态与故障位置。试算只留痕，不改变裁决基线——**试算期间本网段与其他网段仍可照常申请换路并拿到裁决** |
| 登记 | `POST /plans/rate-limits/register` | 装好限速后、实际降容前凭单号登记。登记时**按最新的放行和回执状态复核限速**；方案被覆盖（版本号比对）、复核未通过或已有登记时拒绝请求（409），原记录与核算参数保留 |
| 生效 | （登记成功即生效） | 此后本网段换路放行按新容量和限速核算，申请响应带 `rate_limit_order_id`；同网段再登记新单会覆盖旧生效单（旧单置为 `superseded`） |

限速单全程留痕：`GET /plans/rate-limits?prefix=` 可查全部单（含试算未通过、被覆盖的
历史单与每次登记尝试）。方案被重新 PUT 覆盖后，生效单失效、版本号 +1，旧单登记会被
识别为“方案被覆盖”而拒绝。完整示例见 [API_EXAMPLES.md](API_EXAMPLES.md)。

## 目录结构

```
app/
  models.py    # Pydantic 模型与录入校验（12 台上限、节点/链路/路由一致性、限速单整数上限）
  engine.py    # 核算引擎：2^n 场景穷举 + 断路/环路/超载检测 + 限速值分配
  storage.py   # 进程内存储、设备分组、限速单留痕、asyncio 锁
  main.py      # FastAPI 路由
tests/         # pytest：引擎单测 + API 全流程 + 并发裁决 + 限速单全流程
scripts/
  demo.py            # 端到端演示（in-process ASGI，标准库 + httpx）
  curl_example.sh    # 等价的 curl 调用示例
  plan_a.json        # 环路场景录入载荷
  plan_b.json        # 断路+超载场景录入载荷
  plan_c.json        # 限速单场景录入载荷
Dockerfile
docker-compose.yml
requirements.txt
```

## 启动方式

Docker Compose（推荐）：

```bash
docker compose up -d --build
curl http://localhost:8000/health
# 交互式文档：http://localhost:8000/docs
```

本地直接运行：

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

> 存储为进程内内存，且并发裁决依赖单进程内的 asyncio 锁，因此 Compose/uvicorn 均固定 1 个 worker。

## API 一览

网段前缀（如 `10.11.0.0/16`）含 `/`，作为 query 参数 `prefix` 传递（`/` 需百分号编码为 `%2F`）。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/health` | 健康检查 |
| PUT | `/plans` | 录入或全量覆盖一个目的网段的方案（覆盖后放行状态重置、方案版本 +1、生效限速单失效） |
| GET | `/plans` | 列出所有网段摘要 |
| GET | `/plans/detail?prefix=` | 查询网段全量状态，含全部申请历史与限速单 |
| POST | `/plans/applications?prefix=` | 提交一批设备的换路申请，整批通过或整批退回 |
| POST | `/plans/receipts?prefix=` | 登记已放行设备的成功回执（幂等） |
| POST | `/plans/rate-limits?prefix=` | 开立入口限速单并试算（新容量 + 按优先级的保底速率） |
| GET | `/plans/rate-limits?prefix=` | 列出网段全部限速单（含历史单与登记尝试留痕） |
| POST | `/plans/rate-limits/register?prefix=` | 凭单号登记限速单；按最新放行/回执状态复核，登记后按新容量和限速核算 |

错误码：网段不存在 → 404；设备不属于该网段/未放行先登记回执 → 400/409；
重复申请已在 `pending` 或 `confirmed` 中的设备 → 409；
限速单链路未录入/保底入口未知/新容量高于当前容量 → 400，容量或速率非整数、
超过 100 万或为负 → 422；登记时方案被覆盖/复核未通过/已有登记/试算未通过 → 409。

## 回执到达前后放行结果不同的示例

见 [API_EXAMPLES.md](API_EXAMPLES.md)。简述：申请 `r4` 时因 `r3` 已放行未确认，
`r3=old & r4=new` 组合出现 `r3 <-> r4` 环路而被整批退回；登记 `r3` 成功回执后，
`r3` 强制按新路由 `r3 -> exit` 转发，重新申请 `r4` 即通过。

## 限速单示例：试算后又放行设备，限速单因超容被拒

见 [API_EXAMPLES.md](API_EXAMPLES.md) 的限速单章节。简述：检修链路 `r3->exit`
170 → 70，限速单试算通过；试算期间 `r4` 被放行（新路由把未限速的 80 Mbps 引向
检修链路）；凭单号登记时复核发现 `r4=new` 组合下 `r3->exit` 合计 150 > 70，
登记被拒（409）且原记录保留；把 `r4` 也列入保底后重新试算、登记生效，
后续换路放行即按新容量和限速核算。
